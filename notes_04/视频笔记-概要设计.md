## 核心要点

系统概要设计主要回答四个问题：
1. **用哪些模块**，模块之间怎么交互
2. **用哪些数据**，数据之间有什么关系
3. **技术风险**在哪里
4. **采用什么架构**

---

## 一、模块划分与交互

### 前端模块划分

- 一个页面就是一个模块，差不多够用
- 页面内的小组件不需要单独设计，直接封装即可
- 模块间交互使用前端状态管理工具（如 Pinia / Vuex / Redux 等）

### 后端模块划分

- 根据用例图中的**名词**来划分模块（与页面无关）
- 示例：
  - 增删改查 → 增删改查模块
  - 导入 → 导入模块
  - 统计 → 统计模块
  - 提醒 → 提醒模块
  - 支付 → 支付模块

- 评估是否有技术上无法实现的部分

- **潜在风险点（导入功能）**：

## 四、常见架构

### 三层架构（最经典）

- **表现层**：处理视图（类似 MVC 的 View）
- **应用层**：处理业务逻辑（类似 MVC 的 Controller）
- **数据层**：处理数据（类似 MVC 的 Model）
- 与 MVC 的区别：三层架构的粒度比 MVC **更粗**一些
- 识别方法：看到图画了一条线分两层、DB + Model/Controller/View，基本就是三层架构

### MVC 架构

- 是三层架构的**细化**版本
- 同样分为 Model（数据）、Controller（应用）、View（视图）
- 划分粒度更细，每个模块更小

### 微服务架构

- 每个微服务是一个**完整的模块**（如做权限的、做支付的）
- 每个接口只执行一个函数
- 语言对微服务不重要（可通过 RPC 或 HTTP 交流）
- **难点**：
  - 每个微服务都要独立部署
  - 服务间如何调用、如何治理
  - 配置管理复杂
- 目前 Serverless 主打轻量小型功能，可作为微服务替代方案

## 五、其他常用技术

### 前后端分离

- 前端代码与后端代码**分开**，不混在一起
- 早期 ASP / JSP / PHP 喜欢把 CSS 和 JS 混到 HTML 里，前端很难维护
- 前后端分离后，通过**接口（API）**交流
- **人员也可分离**：大公司会让前端和后端由不同人担任
  - 好处：增加人员可替代性，降低成本（一个后端一万多 + 一个前端一万多 < 一个全栈两万多）
  - 对公司有利，但对全栈个人不利（可替代性增加）

### 负载均衡

- 用多台同样的机器提供服务，分担压力
- 示例：用 Nginx 做转发，分发到两台后端服务器
  - 每台机器只服务 50% 用户，压力减半
  - Nginx 只做转发，速度非常快
- **两大好处**：
  1. **分担压力**：每台机器工作量变少，性能变好
  2. **零停机更新**：更新时先挂掉一台，Nginx 自动把流量转发到另一台；更新完成后再恢复，用户无感知
- **灰度发布**：配合负载均衡，可以只更新一部分机器（如奇数 ID 用新版，偶数 ID 用旧版），让一部分用户先体验新版

### 中间件

- 在架构中**多加一层或一个环节**
- 常见中间件：鉴权、登录验证、安全过滤等
- 数据请求经过必要的中间件后再到达应用层
- 在成熟团队中经常使用

## 简要结论

- 概要设计四要素：模块划分、数据设计、技术风险、架构选择
- 后端模块按用例图中的名词划分，前端按页面划分
- 常见架构：三层架构（最经典）、MVC（三层细化）、微服务（完整模块独立部署）
- 常用技术：前后端分离、负载均衡（分担压力 + 零停机更新 + 灰度发布）、中间件
- 本项目技术风险集中在导入功能（银行账单格式不统一），其余部分简单可行
