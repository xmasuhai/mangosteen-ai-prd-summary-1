# 使用用例图描述功能

> 来源：山竹记账全栈版（Vue 3 + Rails 7 + TSX）｜后端文档撰写与排期 第3节

---

## 核心要点

用例图是描述需求功能的最佳工具，画一张图约 10 秒即可完成，能清晰展示用户能做什么操作。本节逐一用用例图描述了山竹记账的所有功能，并区分了**必做功能**与**选做功能**。

---

## 功能逐一说明

### 功能一：特性介绍（广告页）

- **需求来源**：不是用户需求，是**公司需求**——公司希望产品有商业收入，在用户进入时展示广告
- **用户操作**：
  - 点击下一页 → 进入特性介绍详情
  - 点击跳过 → 跳过广告页
  - 点击开启记账 → 直接进入记账应用
- 用例图完整覆盖了所有操作路径

### 功能二：新增记账（必做）

- 看似简单（点击提交），实际涉及十几个操作节点
- **完整流程**：
  1. 点击开始记账
  2. 进入记账表单，输入：标签、时间、金额
  3. 点击提交
  4. 提交后两种结果：验证失败 → 展示错误信息；验证通过 → 提示记账成功
  5. 还可在记账过程中添加标签（需要单独提交）
- **前后端分工**：
  - 表单、按钮等属于前端工作
  - 两次提交（记账提交、标签提交）→ 后端需提供两个接口
  - 两处验证（校验）→ 后端需处理
- **注意**：用例图描述时可写得笼统些，字段不需要写得太具体

### 功能三：查看记账（必做）

- **操作流程**：
  1. 切换时间范围
  2. 查看记账列表
  3. 向下滑动加载更多
- **后端**：需要提供查看接口和时间范围筛选接口

### 功能四：统计图表（必做）

- 与查看记账类似
- 可切换时间、可切换类型（收入/支出分类）
- **后端**：只需输出一个统计接口即可

### 功能五：登录与登出（必做）

- 看似简单，实际流程较多：
  1. 点击登录
  2. 请求发送验证码
  3. 输入验证码和手机号
  4. 两种结果：登录成功 → 进入首页；登录失败 → 提示错误
  5. 在首页可点击退出登录
- **后端**：仅需两个接口——登录验证接口、发送验证码接口
- **关键观察**：前端工作量约为后端的**三倍**

### 功能六：导出（选做）

- 用户希望将记账数据导出到其他地方展示
- **流程**：选择时间范围 → 确认 → 生成文件 → 下载

### 功能七：导入（选做）

- **流程设计**：
  1. 用户将账单（如信用卡账单、支付宝账单）发送到指定邮箱
  2. 邮件转发到系统邮箱
  3. 系统自动解析邮箱中的账单
  4. 将每条记录提取出来放入记账系统中
- 这是一种可行方案，也可有其他实现方式

### 功能八：记账提醒（选做）

- **流程**：
  1. 用户设置提醒频率（每日提醒 / 每周提醒）
  2. 设置提醒时间点（如每天早上 8 点或晚上 10 点）
  3. 到时间点收到邮件
  4. 用户直接回复邮件（如"打车多少钱、吃饭多少钱"）
  5. 系统通过自然语言分析，自动生成对应记账
- **特点**：前端只需设置频率，后台需做自然语言分析，较为复杂

---

## 注意事项

- **收费不能混入功能需求**：如果导出要收费，收费功能本身是一个**独立需求**，需要先实现收费系统（涉及支付接口等），再在导出/导入中接入收费——不能直接在功能需求里写"导出要收费"
- **需求文档不体现技术语言**：用什么语言实现不会在需求文档中体现，需求文档只描述功能
- **用例图可直接复制到文档**：程序员看不懂文字描述时，根据用例图即可开始开发

## 功能汇总

| 功能 | 类型 | 后端接口数 |
|------|------|-----------|
| 特性介绍（广告页） | 必做 | — |
| 新增记账 | 必做 | 约 2 个 |
| 查看记账 | 必做 | 约 2 个 |
| 统计图表 | 必做 | 约 1 个 |
| 登录与登出 | 必做 | 2 个 |
| 导出 | 选做 | — |
| 导入 | 选做 | — |
| 记账提醒 | 选做 | — |

---

## 简要结论

- 用例图能高效、清晰地描述所有功能需求，直接复制到需求文档中即可指导开发
- 必做功能 5 个（特性介绍、新增记账、查看记账、统计图表、登录登出），选做功能 3 个（导出、导入、记账提醒）
- 前端工作量约为后端的三倍，后端接口需求相对集中
- 收费功能是独立需求，不能随意混入其他功能需求中
- 需求文档不涉及技术语言选择
